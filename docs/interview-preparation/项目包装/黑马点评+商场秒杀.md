原项目介绍
技术栈：Spring Boot、MySQL、Redis、Lua、RocketMQ、Caffeine、MyBatis-Plus

时间：2025.12 - 2026.02

项目简介：一款本地生活服务平台，为用户提供商家信息查询、秒杀优惠券等功能，同时帮助商家进行优惠信息的精准推广与引流。

工作内容：

秒杀防超卖与一人一单：基于 Redis 存储库存及订单标识，结合 Lua 脚本原子化校验库存余量与用户下单资格，保障库存预占与身份校验的严格原子性。

秒杀流程异步化：用户下单成功后，通过 RocketMQ 消息队列异步完成订单创建与后续流程，库存扣减已在 Lua 脚本中同步原子完成，显著提升系统吞吐量与并发处理能力。

未支付订单到期自动关闭：基于 Spring Task 定时任务扫描超时未支付订单并自动关闭，及时释放库存资源。

支付与关单并发控制：采用乐观锁机制解决用户支付与系统自动关单之间的并发竞争问题，保障订单状态流转的正确性。

缓存优化：针对热点 Key 采用逻辑过期策略防止缓存击穿；对不存在的数据缓存空值以解决缓存穿透问题，有效保障系统在高并发下的稳定性。

数据一致性保障：采用"先更新数据库，再删除缓存"策略，删除失败时通过消息队列进行补偿重试，并结合 TTL 兜底，确保缓存与数据库的最终一致性。

多级缓存架构：引入 Caffeine 作为本地一级缓存，Redis 作为分布式二级缓存，构建两级缓存体系，有效提升热点数据访问速度并降低 Redis 集群压力。

滑动窗口限流：基于 Redis + AOP + 自定义注解实现通用限流组件，支持全局、IP、用户等多维度限流策略，防止系统过载、刷券及爬虫攻击。

问题分析拆解
1. 技术选型致命伤：Spring Task 扫描超时订单
当前写法：基于 Spring Task 定时任务扫描超时未支付订单并自动关闭，及时释放库存资源。

问题：在高并发的秒杀场景下，使用 Spring Task 定时任务去扫描数据库表来关闭超时订单是非常危险的做法：

订单表通常数据量极大。定时任务扫表往往意味着全表扫描（O(N) 复杂度）。如果你有用过 MySQL 的执行计划（EXPLAIN）进行分析，就会发现这种查询的 type 极容易退化为 ALL。这会引发大量的磁盘 I/O，导致数据库 CPU 瞬间飙升至 100%，甚至引发锁表，直接拖垮主库，影响核心链路。

定时任务的执行周期存在时间差（例如每分钟执行一次），会导致库存释放不及时，严重影响真实用户的购买转化率。

这是很多培训班课程里的常见做法，不是说 Spring Task 扫库不能用，而是要看具体场景，如果数据量不大且不在乎时效性的话，当然可以用。

另外，如果必须一定要用定时任务扫表，还可以做一些针对性优化，例如：你可以通过在 SQL 中增加时间范围限制，配合合适的索引，将全表扫描（O(N)）优化为局部索引扫描。比如，只查询过去 30 分钟内未支付的订单：SELECT id FROM order WHERE status = 0 AND create_time >= DATE_SUB(NOW(), INTERVAL 30 MINUTE); 并且在数据库中建立 (status, create_time) 的联合索引。这样，查询的 type 就会从 ALL 变成 range，极大减少扫描的数据量。

虽然这种做法解决了全表扫描的致命伤，但依然存在以下几个无法回避的痛点（你可以把这些点作为面试时和面试官拉扯的深度素材）：

1.
瞬时数据量依然巨大，数据库压力并未根除：秒杀的特点是"短时间内涌入海量订单"。即使你只扫描最近 5 分钟的订单，这 5 分钟内也可能产生了十万级甚至百万级的订单记录。定时任务将这十几万条数据从 MySQL 查出来，加载到应用内存中，再逐个判断、修改状态，这个过程对数据库的 CPU、磁盘 I/O 以及应用服务器的内存（极易引发 Full GC）依然是巨大的负担。而秒杀期间，数据库的性能应该全部让步于核心的"下单扣库存"链路。

2.
时效性差，导致"黄金库存"被白白占用：定时任务本质上是"轮询（Pull）"机制，必定存在时间差。假设你设置每 1 分钟执行一次扫描任务，订单 15 分钟超时。如果一个订单在第 15 分钟零 1 秒超时，它可能要等到第 16 分钟定时任务触发时才会被关闭并释放库存。在秒杀场景下，库存就是生命线。这 1 分钟的延迟，意味着真正想买的用户看到的是"已售罄"，等 1 分钟后库存释放了，用户早就流失了，严重影响转化率。

3.
分布式环境下的并发冲突与重复执行：现在的服务都是集群部署（多个节点）。如果只是简单用 Spring Task 的 @Scheduled 注解，集群中的 3 台机器会在同一时间触发扫表任务。这就需要引入分布式锁或者使用 XXL-JOB 这样的分布式任务调度框架来进行分片广播。无形中把一个简单的关单逻辑搞得非常复杂，且增加了极大的锁争用开销。

建议改法（任选其一）：

1.
RocketMQ 延迟消息 / RabbitMQ 延迟队列（推荐）：下单成功后，立刻向 MQ 投递一条延迟消息（如 15 分钟）。15 分钟后，消费者准时收到消息并核对订单支付状态（状态机）。若未支付，则执行关单并回滚库存。库存回滚建议走补偿消息（再发一条 MQ），避免直接在消费者里操作 DB 导致事务爆炸。

2.
Redisson 延迟队列（备选）：如果公司技术栈没有引入重量级的 MQ，可以使用 Redisson 延迟队列来实现，轻量且高效。Redis 虽然有 AOF/RDB，但在极端宕机情况下仍有丢数据风险。建议配合一个低频的（如每小时一次）Spring Task 扫表作为兜底，专门捞取漏处理的极少数超时订单。不过，极端高并发下，Redis 内存 + 调度线程容易成为瓶颈。另外，可靠性相对 MQ 稍弱，订单场景需要权衡。

RocketMQ 延迟消息介绍：

RocketMQ 4.x 版本及其之前的版本支持基于预定义的延时等级的延时消息处理。消息发送者可以指定一个延时等级（如 1s、5s、10s 等），然后消息会在相应的延时级别到达后被发送到消费者队列。这些延时等级是固定的，不能灵活配置。

RocketMQ 5.0 基于时间轮算法引入了定时消息，解决了延时级别只有 18 个、延时时间不准确等问题。RocketMQ 5.0 对延时消息的优化的详细介绍可以看看这篇文章：弥补延时消息的不足，RocketMQ 基于时间轮算法实现了定时消息！。

RabbitMQ 延迟队列实现方式：

1.
DLX + TTL（RabbitMQ 3.6.x 之前）：将消息发送到一个设置了 TTL 的队列中，当消息过期后，会被转发到另一个设置了 DLX（Dead Letter Exchange，死信队列）的队列中，消费者监听这个 DLX 队列来获取延迟消息。

2.
延迟消息插件（RabbitMQ 3.6.x 开始，推荐）：RabbitMQ 官方提供了延迟队列插件 rabbitmq_delayed_message_exchange。声明 x-delayed-message 类型的 Exchange，消息发送时指定消息头 x-delay（毫秒）将消息进行延迟投递。插件支持的最大延迟时间：(2^32)-1 毫秒，约 49 天。相比 DLX + TTL，更简单方便，解决了消息阻塞问题。

改后示例：

1.
基于 RocketMQ 延迟消息实现订单超时精准关闭，下单即投递延迟消息，超时后自动消费并释放库存。

2.
引入 RocketMQ 延迟消息替代数据库定时扫描，将订单超时关闭的实时性提升至秒级，同时数据库负载下降 90% 以上。通过消息重试和幂等校验，确保百万级订单场景下库存准确无误。

2. 秒杀流程异步化描述逻辑反了
当前写法：用户下单后通过 RocketMQ 异步完成库存扣减与订单创建。

问题：在高并发秒杀中，库存扣减必须同步执行。如果将扣库存放在异步队列（RocketMQ）中处理，会导致由于消息积压产生的"超卖"或"库存虚假充足"风险。面试官会质疑："如果异步扣减失败了怎么办？用户看到有货但下单失败，用户体验如何保证？"

库存预扣 vs 最终扣减：

其实很多大厂的真实方案是这样的：

1.
第1步（同步）：用户点击秒杀，系统用 Redis + Lua 同步预扣库存，扣成功才给用户"下单成功"的反馈。这一步是实时的，确保库存不会超卖。

2.
第2步（异步）：订单创建的完整流程（落库、积分、通知商家等）丢给 RocketMQ 异步处理。这时候库存已经在 Redis 里扣了，异步任务只是"把状态落库"，失败了可以重试，不影响"有没有货"这个核心判断。

这样设计的好处是：

用户看到的"成功"是真的成功（库存已占住）

异步任务即使积压，也只是"订单详情"延迟展示，不会出现"有货但下单失败"

《后端面试高频系统设计&场景题》中“如何设计秒杀系统”这篇文章也有提到这个问题，建议顺带看看库存扣减部分。

建议改法：

1.
Redis + Lua 脚本（推荐）：利用 Redis 命令执行的单线程特性（注：Redis 6.0+ 引入多线程 I/O 处理网络读写，但命令执行仍为单线程），通过 Lua 脚本在内存中完成"校验库存 -> 扣减库存"的一步到位的原子操作。只有 Lua 返回成功，才认为抢购成功并发送 RocketMQ 消息。

2.
本地预扣 + 数据库行锁（备选）：如果并发量在万级以下，可以采用数据库存储过程或 UPDATE ... SET stock = stock - 1 WHERE stock > 0 的行锁机制，但这种方式对数据库压力较大，不建议在超高并发场景使用。

改后示例：

用户下单成功后，通过 RocketMQ 消息队列异步完成订单创建与后续流程，库存扣减已在 Lua 脚本中同步原子完成，显著提升系统吞吐量。

3. 数据一致性保障的补偿机制太教科书
当前写法：采用"先更新数据库，再删除缓存"策略，删除失败时通过消息队列进行补偿重试，并结合 TTL 兜底，确保缓存与数据库的最终一致性。

问题：这种描述过于理想化，忽视了分布式环境的复杂性。面试官必然会追问：如果更新 DB 成功但发 MQ 失败怎么办？MQ 挂了怎么办？多次重试依然失败如何感知并修复？只提补偿而不提"闭环设计"，体现不出高级开发者对生产环境极端异常的防御能力。

建议改法（构建四步闭环）：

1.
Canal 异步订阅 Binlog（彻底解耦）：业务层只负责更新数据库，通过 Canal 伪装从节点监听 MySQL Binlog，实时投递变更事件到 MQ，由独立的消费者执行缓存淘汰。

2.
本地消息表 + 指数退避重试（强一致投递）：若受限于技术栈不引入 Canal，可在更新 DB 的同一本地事务中写入"本地消息表"，由独立线程轮询投递缓存清理任务；失败后按 1s、5s、10s、30s 递增重试，保障消息绝对不丢。

3.
死信队列（DLQ）+ 自动化告警（异常感知）：设定明确的最大重试阈值（如 5 次）。耗尽后将消息流转至死信队列，并触发监控（钉钉/企微/邮件）告警，通知人工介入或触发自动化修复脚本，形成完整的异常处理闭环。

4.
定期扫描兜底（终极防线）：部署定时任务（如每小时执行一次），离线比对核心数据的 DB 与缓存状态，对游离的不一致数据进行最终兜底修复。

改后示例：

侧重 Canal 解耦（推荐，针对商家信息/配置变更）：针对商家信息变更场景，整合 Canal 监听 Binlog 异步触发缓存淘汰，配合 MQ 指数退避重试与死信告警构建异常自愈闭环，保障数据最终一致性，人工介入率降低 90%。

侧重事务严谨性（推荐，针对核心订单/资金流转）：针对核心订单状态流转场景，基于本地消息表保障业务更新与缓存清理的事务原子性，结合失败指数退避重试与定时离线对账兜底，有效收敛高并发下的数据脏读现象。

通用一致性兜底方案（备选，万金油写法）：基于 Cache Aside 模式结合 RocketMQ 可靠重试与死信告警重构缓存一致性体系，消费端基于业务 ID 实现幂等，配合定时离线比对防线，实现脏数据零残留。

4. 缓存描述过于八股
当前写法： 将“逻辑过期”、“缓存空值”、“先写 DB 再删缓存”、“Caffeine+Redis 多级缓存”分列成了四条工作内容。

问题：

堆砌八股： 这种写法显得非常冗长，且缺乏宏观设计思维。面试官一看就知道是在背诵培训班题库。真实生产中，这些技术点是组合在一起解决具体业务痛点的。

逻辑硬伤（致命）： 很多同学喜欢写“Caffeine + Redis 两级缓存 + 逻辑过期”。这在实现上是个深坑：Caffeine 本身靠物理过期，而逻辑过期不设物理 TTL。如果 Redis 逻辑过期了，后台线程重建了缓存，本地 Caffeine 怎么感知？如果不引入 MQ 广播或 Pub/Sub，两级缓存之间的一致性会让你在面试中被问死。

过度设计： 在 98% 的场景中，单层 Redis 就足够了。引入本地缓存会带来极其痛苦的数据一致性问题、应用内存危机以及负载均衡导致的低命中率。

为什么绝大多数项目不用多级缓存？

在 98% 以上的常规业务中，单用一层 Redis 就足够应对了。强行引入 Caffeine 这样的本地缓存，会带来巨大的架构灾难：

1.
极其痛苦的数据一致性问题：这是最大的阻碍。如果 Redis 里的数据更新了，你怎么通知部署在 10 台不同服务器上的微服务去清理它们各自本地的 Caffeine 缓存？这就需要引入 Redis Pub/Sub 或者 RocketMQ 广播消息。一旦广播失败，某个节点就会一直给用户返回旧数据（也就是所谓的"脏读"），这种排错过程堪称噩梦。

2.
应用服务器的内存危机：本地缓存是和你的 Java 进程共享 JVM 内存的。如果不严格控制容量和驱逐策略，极易引发频繁的 Full GC，甚至直接导致 OOM（内存溢出），直接把服务拉垮。

3.
低命中率的尴尬：现在的微服务都是多节点部署，前端请求经过负载均衡（如 Nginx）轮询打到不同的机器上。用户第一次请求打到 A 机器，A 机器预热了本地缓存；第二次请求打到 B 机器，B 机器本地依然没数据，还要去查 Redis。如果不配合一致性哈希路由，本地缓存的命中率其实很难看。

那多级缓存到底用在哪里？

虽然坑多，但在以下两类真实场景中，多级缓存是毫无争议的最优解：

1.
读写比例极其夸张的"绝对热点"业务：当 QPS 达到十万、百万级别，连 Redis 集群的网卡带宽都快被打满时，就必须用本地缓存去替 Redis 挡子弹。

典型场景：淘宝双十一的首页商品推荐、微博热搜榜单、秒杀活动商品详情页。

特点：这些数据几分钟甚至几小时都不变，但每秒有无数人在刷。即便短暂出现各节点数据不一致，业务上也能容忍。

2.
几乎不变化的静态字典/配置数据：

典型场景：省市区地址库、物流公司的网点路由表、各种业务状态枚举字典。

特点：这类数据可能一个月都不改一次，每次查 Redis 都要走一次网络 I/O，完全没必要。直接应用启动时全量加载到 Caffeine 里，性能可以做到极致。

建议改法：不要为了堆砌名词而引入多级缓存。将防御策略（穿透、击穿、雪崩）与具体业务场景绑定，并给出一套逻辑自洽的单层或双层架构。

改后示例：

1.
基于 Redis 缓存支撑热点商品查询，通过布隆过滤器拦截无效请求、空对象缓存兜底防御缓存穿透；配合热点数据提前预热与随机 TTL 策略规避缓存击穿与雪崩，大促期间核心接口响应稳定在 50ms 内。

2.

常见面试问题拷打
为什么重构秒杀流程？
在做秒杀模块时，我发现最大的矛盾是防超卖的强一致性要求与高吞吐量之间的冲突。最初的版本很容易犯一个错，就是把扣库存的操作直接交给 MySQL 甚至异步去扣，这在并发极高时必然会导致超卖。所以我先把核心流程拆成了两步：同步预扣 + 异步落库。

第一步，所有的秒杀请求先打到 Redis，我用 Lua 脚本把判断库存和扣减库存封装成一个原子操作。只要 Lua 脚本返回成功，物理上绝对不会超卖。第二步，拿到资格的用户，我会立刻把交易快照发给 RocketMQ，然后快速给前端响应。后台消费者再以数据库能承受的平缓速度慢慢执行复杂的订单 INSERT 操作。这种做法既保证了数据的绝对安全，又把接口 QPS 提升了十倍。

为什么不用 Spring Task 关闭超时订单？
这是一个业务演进的过程。最开始确实是用 Spring Task 每分钟扫表。为了优化，我还特意建了复合索引，并限制只扫描近 30 分钟的订单。但压测时我发现，在秒杀这种瞬时海量数据的场景下，即使是局部索引扫描，对主库的 I/O 和 CPU 依然是巨大的消耗。而且定时任务的轮询存在时间差，导致宝贵的秒杀库存不能在第一时间释放给其他真实用户。所以我全面推翻了拉模式，改用基于 RocketMQ 的推模式。订单创建时发一条 15 分钟的延迟消息，时间一到精准触发状态校验。把全表扫描的 O(N) 复杂度降维打击变成了 O(1) 的按需消费，彻底解放了数据库的查询压力。

你简历里写了 Canal 加上死信队列，为什么要搞得这么复杂？
单纯采用双删或者先更新 DB 再删缓存，在理想环境下没问题。但我考虑到生产环境必须对异常有敬畏心。如果业务代码刚更新完 MySQL，还没来得及发消息或者删缓存就宕机了，就会出现永久的脏数据。所以我引入了 Canal 监听 Binlog，把缓存清理动作和业务代码彻底解耦。只要 MySQL 落盘了，后续的清理指令就一定能发出来。同时，网络抖动可能导致消费失败，所以我设计了阶梯式的指数退避重试。考虑到不能无限重试导致消息积压，我设定了最大 5 次的阈值，超过后扔进死信队列并触发预警。我还配套写了离线对账脚本进行最终兜底。这是一个从物理层防御到异常自愈的完整闭环。

为什么要用 Redis 锁加 MySQL 乐观锁双重机制？
为了兼顾系统的极致性能和绝对安全。单靠 MySQL 乐观锁虽然能防住脏写，但在遭遇回调重试风暴或高并发竞态时，会让大量无效请求长驱直入，不仅白白消耗应用服务器算力，还会导致数据库 CPU 飙升。

所以我引入了分层防御机制：前置利用 Redis 分布式锁极高的吞吐量做粗粒度拦截，把绝大多数并发请求挡在数据库之外，实现快速失败；而底层的 MySQL 乐观锁则作为最终的兜底防线，抵御 Redis 宕机、锁失效等极端边缘场景，确保订单状态流转的 100% 正确性。

你的海量数据导出提到了”游标分页”，如果查到第 500 万条数据，MySQL 深分页怎么优化？
这是海量数据处理必考的”拦路虎”。

如果直接用常规的 LIMIT 5000000, 1000，MySQL 会在底层扫描 500 万零 1000 行数据，然后丢弃前 500 万行，导致严重的磁盘 I/O 和 CPU 消耗，查询极慢。

我在项目中采用了基于主键（或自增 ID）的游标分页法。每次查询时，记录下上一批数据最后一条的 ID（last_max_id），下一次查询的 SQL 改写为：

SELECT id, order_sn, amount FROM `order` WHERE id > #{last_max_id} ORDER BY id LIMIT 1000
这样 MySQL 可以直接通过主键 B+ 树索引定位到起始位置，时间复杂度为 O(log N)，相比 LIMIT offset, size 的 O(N) 扫描有质的提升，彻底解决了深分页的性能衰退问题。

当然，为了将磁盘 I/O 和网络传输开销降到最低，生产环境中严格禁止使用 SELECT *，必须明确指出需要导出的具体字段，例如 SELECT id, order_sn, amount FROM order WHERE id > #{last_max_id} LIMIT 1000。如果导出字段能命中覆盖索引，性能可以压榨到极致。

你提到用布隆过滤器防穿透，那如果数据库里的商品删除了，布隆过滤器怎么同步删除？
这是面试官非常喜欢挖的一个坑。

布隆过滤器的底层是一个巨大的二进制位图（BitMap），初始状态下全都是 0。当你向系统添加一个商品（比如商品 ID 是 1001）时，系统会用几个不同的 Hash 函数对 1001 进行计算，得出几个数组下标，然后把这些位置上的 0 统统变成 1。这就像是给这个商品盖了几个专属的“指纹印”。

假设过了一段时间，商家把商品 1001 下架并从数据库删除了。按理说，我们应该把布隆过滤器里属于 1001 的那些 1 重新改回 0。

但是，标准的布隆过滤器绝对不允许这种操作！

原因在于哈希碰撞（Hash Collision）。有可能系统里还有一个热卖的商品 1002，它经过 Hash 计算后，跟 1001 碰巧共享了某一个甚至几个”1”的位置。如果你为了删除 1001，强行把那些 1 改回了 0，就会导致商品 1002 的指纹也被破坏了。这时候如果有真实用户来查询 1002，布隆过滤器检测到该 key 的所有 Hash 位不全为 1，判定”可能不存在”并拦截请求，这就造成了严重的误杀（假阳性），正常的业务直接瘫痪。

针对这个问题，我的解决方案是**”布隆过滤器前置拦截 + 空对象缓存动态兜底”**：

大部分恶意构造的非法请求，会在布隆过滤器这一层被直接挡掉

对于那些”曾经存在但后来被删除”的商品，请求确实会穿透布隆过滤器打到数据库

此时由于数据库查不到数据，我会立刻在 Redis 中存入一个带有极短过期时间（如 30 秒）的”空对象”

这样的话，当 MySQL 查明这个商品 1001 确实已经被删除后，立刻在 Redis 里塞入一条空数据：Key = 1001, Value = Null，并设置一个很短的过期时间（比如 30 秒）。这样后续的相同请求就会命中空对象直接返回，既规避了布隆过滤器无法删除的缺陷，又完美保护了底层数据库。

顺便补充一点：虽然学术上可以通过引入**计数布隆过滤器（Counting Bloom Filter）或者布谷鸟过滤器（Cuckoo Filter）**来实现元素的删除，但考虑到引入新型组件带来的运维成本以及额外的内存开销，在绝大多数真实的电商架构中，采用传统布隆过滤器拦截加上空对象极短 TTL 兜底，是性价比最高、最稳妥的生产级方案。

为什么要引入 COLA 状态机来管理订单状态？用 if-else 和常量控制不好吗？
如果只是简单的”待支付、已支付”两个状态，if-else 确实足够了。但本地生活平台的订单生命周期非常复杂，涉及待支付、已支付、商家接单、已核销、退款中、已退款等十几个状态，以及用户、商家、系统超时等多种触发事件。

如果用硬编码，代码里会充斥着类似 if (status == PAID && event == REFUND) 的面条代码，极易产生 Bug（比如错误地给未支付的订单执行了退款逻辑）。

引入 COLA 状态机，我将”状态（State）”、”事件（Event）”和”动作（Action）”进行了解耦。所有的状态流转规则都在配置类中统一注册，业务代码只需要关心触发什么事件，状态机引擎会自动校验当前状态是否合法并执行对应动作。这不仅杜绝了非法的状态跃迁，也让核心业务逻辑的扩展性得到了质的提升。

既然你们用了 RocketMQ 处理各种异步流程，如果突发异常导致消息大量堆积怎么办？
处理消息堆积必须有一套应急预案。如果在生产环境发生报警，发现消息严重积压：

第一步：立刻排查消费端是否出现了死循环、慢 SQL 或者第三方接口超时，导致消费速度断崖式下跌。如果是代码 Bug，需要紧急修复并重新发布。

第二步：如果是纯粹的突发流量过大导致堆积，传统的做法是增加消费者机器数量。但需要注意：同一消费者组内的消费者实例数受限于 Topic 的队列数，当消费者数量超过队列数时，多余的消费者将无法分配到队列，处于空闲状态。

第三步：如果增加机器依然处理不过来，我会采用**”临时扩容降级”**的方案——写一个临时的应急消费者程序，只负责以极快的速度把堆积的消息搬运到一个有着几十个队列的”临时扩容 Topic”中，然后启动几十台应急消费者机器去消费这个新 Topic，以十倍甚至百倍的速度快速消化掉堆积的业务。

你用了 Sa-Token 做认证，为什么不用 Spring Security？
Spring Security 功能确实强大，但对于大多数业务系统来说有点”杀鸡用牛刀”——配置复杂、学习曲线陡峭，很多功能根本用不上。

Sa-Token 更轻量，API 设计更符合国内开发习惯。我项目中主要用到了：

Token 认证：支持自动续签和踢人下线

RBAC 权限模型：角色-权限-菜单三级控制

注解式鉴权：@SaCheckRole、@SaCheckPermission 一行代码搞定

当然，如果公司有统一的安全规范要求用 Spring Security，我也会按规范来。技术选型最终还是要服务于业务和团队。

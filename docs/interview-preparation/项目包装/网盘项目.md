### 1.4 个人职责

简单描述自己做了什么，解决了什么问题，带来了什么实质性的改善。突出自己的能力，不要过于平淡的叙述。

下面列举一些可选的个人职责介绍（不要原封不动的 copy，也不要都按照我的来写，适当润色一下，结合自己的实际情况来写）：

1. 基于 SpringSecurity + JWT 实现了登录认证，实现了同端互斥登录和强制下线功能。
2. 权限模型使用业界主流的 RBAC，引入了 VIP 用户机制，VIP 用户上传下载速度不受限制。

8. 基于 Elasticsearch 实现文件的全文检索，整合 Canal + RabbitMQ 将 MySQL 增量数据（如文件信息）同步到 Elasticsearch。
9. 基于 AOP + 注解统一日志记录，并结合 Spring 框架实现全局异常处理。
10. 基于 JUnit + Mockito 编写测试代码，部署 SonarQube 分析代码质量并集成 JaCoCo 生成单测覆盖率报告。
11. 基于 Gitlab CI 搭建持续集成环境，集成测试、质量分析等步骤，保障项目质量。

### 1.5 可优化的方向

- **第三方登录**：引入第三方登录，例如 Github、Gitee、微信，具体思路可以参考星球的分享：<https://t.zsxq.com/18ZIzSBPH>
- **文件在线预览**：实现常见文件类型（例如 doc、docx、ppt、pptx 等等）的在线预览功能，具体思路可以参考星球的分享：<https://t.zsxq.com/19Kp1fAoI>
- **分库分表**：数据量太大且通过缓存、索引等优化手段无法解决问题的情况下再考虑分库分表，推荐基于 ShardingSphere 实现。
- **读写分离**：数据库读压力比较大的情况下可以考虑，推荐基于 ShardingSphere 实现。
- **在线聊天室**：基于 Netty + Websocket 实现一个在线聊天室，登录系统的用户可以进入同一个聊天室聊天。这个功能适合加在很多系统中作为一个小亮点，挺实用的。

### 3.2 认证授权

认证授权是开发难度相对较大的一个功能，对于在校学生来说。

认证授权可以基于下面三个框架来做：

| 框架 | 特点 |
|------|------|
| **Sa-Token** | 轻量级 Java 权限认证框架，支持认证授权、单点登录、踢人下线、自动续签等功能。开箱即用的功能更多，使用也更简单。 |
| **Spring Security** | Spring 官方安全框架，能够用于身份验证、授权、加密和会话管理，是目前使用最广泛的 Java 安全框架。 |
| **Shiro** | Java 安全框架，功能和 Spring Security 类似，但使用起来更简单。 |

一般来说，Spring Security 用的最多，最权威。国人开源的 Sa-Token 易用性更强，也可以使用。个人的话，更推荐 Spring Security，因为 Sa-Token 提供的开箱即用的功能太多，面试反而不太好发挥。

### 3.3 文件存储

面试的时候，面试官可能会问你网盘的底层存储是什么以及为什么这样选择。

当你说选择的是开源文件存储系统的话，面试官可能会追问你（这里以 MinIO 为例）：

1. 有没有对比过其他开源文件存储系统？
2. 为什么最后用 MinIO？MinIO 有什么优势？
3. MinIO 的纠删码是什么？有什么用？
4. MinIO 如何实现高可用？如果某个节点出现故障，数据仍能正常访问吗？

网盘的底层存储一般可以选择：

- 本地磁盘（不推荐）
- 对象存储服务（比如阿里云 OSS、腾讯云 COS）
- 开源文件存储系统（比如 FastDFS、MinIO、Ceph）

> 我这里是以 MinIO 为例进行说明的，不代表你就必须也按照这个来写。你也可以选择对象存储服务如阿里云 OSS，或者其他开源文件存储系统例如 Ceph。

#### 本地磁盘

不推荐使用本地磁盘作为网盘的底层存储，缺点如下：

- **扩展性太差**：不支持存储空间的动态扩展，假如我们的磁盘空间不够用了，你想扩展存储空间会非常麻烦。
- **功能性太弱**：不具备自动备份、数据恢复等功能，需要我们自己开发，增加了开发和维护的难度。
- **可靠性较差**：本地磁盘出现硬件故障的话，可能会导致数据丢失。
- **性能较差**：本地磁盘的读写速度相对较慢，无法满足大规模并发访问的需求，容易导致网盘响应变慢，甚至崩溃。

**推荐使用对象存储或者开源文件存储系统来做。**

#### 对象存储服务（OSS）

对象存储服务（Object Storage Service，OSS）是一种海量、安全、低成本、高可靠的云存储服务，适合存放任意类型的文件。容量和处理能力弹性扩展，多种存储类型供选择，全面优化存储成本。

常见的云服务商如阿里云、腾讯云、七牛云、AWS 等都提供了对象存储服务。这里以阿里云 OSS 为例说明。

> 阿里云 OSS Java SDK 参考文档：<https://www.alibabacloud.com/help/zh/object-storage-service/latest/java-introduction>

**面试常见问题：**

1. **项目是如何使用阿里云 OSS 的？**
   直接在项目中使用对应语言的 SDK 即可实现存储空间和文件增删改查，前提是你已经开通了 OSS 服务并且已创建 AccessKey。

2. **为什么要使用 OSS（有什么好处）？**
   - 可靠性强：可提供 99.9999999999%（12 个 9）的数据持久性，99.995% 的数据可用性。
   - 安全性强：支持防盗链配置、基于 SSL/TLS 的 HTTPS 加密传输、文件版本控制、细粒度文件读写权限控制等。
   - 扩展性强：不限制存储空间大小，可以根据所需存储量无限扩展。
   - 成本较低：无需传统硬件的采购、部署和运维，支持按量付费。
   - 接入方便：提供标准的 RESTful API 接口、丰富的 SDK 包、客户端工具、控制台。

3. **Bucket 是什么？**
   在阿里云 OSS 中，Bucket（存储空间）是一个基本容器，用于存储数据对象（即文件）。可以将 Bucket 视为一个高级的"文件夹"，它存储数据并且可以全球访问，依赖于用户配置的权限和策略。

4. **如何加速 OSS 的访问？**
   直接访问 OSS 资源，访问速度会受到 OSS 的下行带宽以及 Bucket 地域的限制。如果通过 CDN 来访问 OSS 资源，带宽上限更高，并且可以将 OSS 的资源缓存至就近的 CDN 节点，通过 CDN 节点进行分发，访问速度更快，且费用更低。

5. **如何防止 OSS 中的文件被盗链？**
   OSS 支持对存储空间（Bucket）设置防盗链，即通过对访问来源设置白名单的机制，避免 OSS 资源被其他人盗用。

6. **阿里云 OSS 支持版本控制吗？**
   支持。版本控制允许用户保存和管理存储在 Bucket 中的每个对象的多个版本，可以访问和恢复任何先前版本的对象。

#### MinIO（开源文件存储系统）

相比较于对象存储来说，开源文件存储系统提供的功能一般要少一些，但其优势在于比较灵活，比较适合中小型项目。

开源文件存储系统一般选择 MinIO 和 FastDFS 的多一些。个人推荐使用基于 Go 语言开发的 MinIO，其功能非常强大，并且这是世界上最快的对象存储，没有之一。

根据 MinIO 官网介绍：

- MinIO 提供高性能、与 S3（全球范围内达到共识的对象存储的协议，由亚马逊 AWS 制定）兼容的对象存储系统，让你自己能够构建自己的云储存服务。
- MinIO 原生支持 Kubernetes，它可用于每个独立的公共云、每个 Kubernetes 发行版、私有云和边缘的对象存储套件。
- MinIO 是软件定义的，不需要购买其他任何硬件，在 GNU AGPL v3 下是 100% 开源的。
- MinIO 使用纠删码、Checksum 来防止硬件错误和静默数据污染。在最高冗余度配置下，即使丢失 1/2 的磁盘也能恢复数据。

> ⚠️ **注意**：MinIO 目前已经不免费商用了，并且价格比较贵。MinIO 官网已经写的非常清楚，你用了开源版 MinIO，就必须得开源自己的源代码，很显然这并不适用于公司。如果你想找到免费商用版本的话，可以选择之前基于 Apache License 2.0 协议的版本，比如 [RELEASE.2021-04-22T15-44-28Z](https://github.com/minio/minio/releases/tag/RELEASE.2021-04-22T15-44-28Z)。

- MinIO 中文官网：<https://www.minio.org.cn/>
- GitHub 地址：<https://github.com/minio/minio>

**面试常见问题：**

1. **有没有对比过其他开源文件存储系统？**
   也考虑过使用 FastDFS，但经过详细对比之后发现 MinIO 具有下面这些优势：

   | 对比维度 | MinIO | FastDFS |
   |----------|-------|---------|
   | 安装部署 | 安装部署简单，开箱即用 | 安装部署较为复杂 |
   | 官方文档 | 有详细的官方文档参考 | 没有官方文档，参考资料少 |
   | 社区活跃度 | 公司项目，社区活跃，更新频繁 | 个人项目，社区不活跃，更新不频繁 |
   | UI 界面 | 自带 UI 界面，开箱即用 | 默认不带 UI 界面 |
   | 性能 | 世界上最快的对象存储，没有之一 | 性能相对较弱 |
   | S3 协议 | 支持 S3 协议，兼容主流云存储服务 | 不支持 S3 协议 |
   | 云原生 | 提供与 Docker、K8s 等深度集成方案 | 云原生支持不友好，需自行改造 |

2. **为什么最后用 MinIO？MinIO 有什么优势？**
   上一个问题的答案已经表明了 MinIO 的优势。

3. **MinIO 的纠删码是什么？有什么用？**
   多副本策略和纠删码（Erasure Code，简称 EC）是存储领域常见的两种数据冗余技术。相比于副本策略，纠删码具有更高的磁盘利用率。

   | 对比维度 | 多副本（3 副本） | 纠删码（n+m） |
   |----------|:------------:|:----------:|
   | 磁盘利用率 | 1/3 | n/(n+m) |
   | 计算开销 | 几乎没有 | 高 |
   | 网络消耗 | 较低 | 较高 |
   | 恢复效率 | 较高 | 较低 |

   分布式 MinIO 使用 Reed-Solomon（简称 RS）纠删码将对象拆分为 n 个数据块和 m 个校验块。默认是拆分成 N/2 数据块和 N/2 奇偶校验块，其中 N 是磁盘数量。这意味着即使丢失集群中一半的节点或硬盘，也仍然可以通过剩余的数据块和奇偶校验块来恢复数据。

   > 扩展阅读：[有趣的纠删码(Erasure code)](https://www.jianshu.com/p/4ebf2dfd39bf)、[纠删码 Erasure Coding（分布式存储系统）](https://zhuanlan.zhihu.com/p/23172828)

4. **MinIO 如何实现高可用？如果某个节点出现故障，数据仍能正常访问吗？**
   - 单机 MinIO 服务存在单点故障，可以通过分布式的方式实现高可用性。
   - 分布式 MinIO 至少需要 4 个节点（4 台服务器）才能发挥其功能，自动引入纠删码功能。
   - 只要有 N/2 个节点在线，MinIO 中存储的数据就是安全的，并且可以进行读取操作。但写入新对象或更新现有对象时，必须至少有 N/2+1 个节点在线。

   > 以一个 8 节点的 MinIO 集群为例：假设有 4 个节点宕机，则剩余的 4 个节点仍然可以保证数据的可读性。但写入操作必须至少有 5 个节点在线。

### 3.5 文件多线程下载

除了上面提到的文件上传之外，本项目还提到了基于 CompletableFuture + 线程池实现大文件的多线程下载。

**基本流程：**

1. **获取文件总大小**：使用 HTTP HEAD 请求来获取文件的总大小。
2. **计算分块下载的范围**：根据线程数，将文件分成多个部分，为每个部分计算开始和结束的字节位置。
3. **设置线程池和并发下载**：为每个文件分块创建一个下载任务，并使用 CompletableFuture 在线程池中异步执行。
4. **下载数据到临时文件**：每个 CompletableFuture 任务下载指定范围的数据到一个临时文件。
5. **合并临时文件**：所有分块下载完成后，合并这些临时文件成为一个完整的文件。
6. **清理和完成**：删除所有临时文件，处理任何异常，确保资源被正确释放。

> 除了要搞懂文件多线程下载的基本流程之外，建议顺便把 CompletableFuture 这一知识点顺带着复习一下，面试也可能会问的。

### 3.6 文件分享失效

文件分享失效属于延迟任务的一个场景，在网盘系统中很常见，比如我们设置分享的文件在固定的时间（如 30 天）之后失效，类似于订单失效。

延迟任务的常见实现方法有：

- 消息队列比如 RocketMQ 的延时/延迟消息（**首选**）
- Redisson 内置的延时队列 DelayedQueue

我们这里假设你的项目没有使用消息队列，但使用了 Redis。这个时候我们需要考虑的是如何借助 Redis 来实现延时任务的功能。

基于 Redis 实现延时任务的功能无非就下面两种方案：

1. Redis 过期事件监听
2. Redisson 内置的延时队列

> 面试的时候，你可以先说自己考虑了这两种方案，但最后发现 Redis 过期事件监听这种方案存在很多问题，因此你最终选择了 Redisson 内置的 DelayedQueue 这种方案。

**面试常见问题：**

1. **Redis 过期事件监听实现延时任务功能的原理？**
   Redis 2.0 引入了发布订阅 (pub/sub) 功能。Redis 中有很多默认的 channel，其中 `__keyevent@0__:expired` 是一个默认的 channel，负责监听 key 的过期事件。也就是说，当一个 key 过期之后，Redis 会发布一个 key 过期的事件到 `__keyevent@<db>__:expired` 这个 channel 中。我们只需要监听这个 channel，就可以拿到过期的 key 的消息，进而实现了延时任务功能。
   
   > 这个功能被 Redis 官方称为 keyspace notifications，作用是实时监控 Redis 键和值的变化。

2. **Redis 过期事件监听实现延时任务功能有什么缺陷？**
   - **时效性差**：过期事件消息是在 Redis 服务器删除 key 时发布的，而不是一个 key 过期之后就会直接发布。Redis 采用的是定期删除 + 惰性删除策略，因此存在 key 到了过期时间但还未被删除的情况。
   - **丢消息**：Redis 的 pub/sub 模式中的消息并不支持持久化。当没有订阅者时，消息会被直接丢弃。
   - **多服务实例下存在消息重复消费的问题**：Redis pub/sub 目前只有广播模式，所有订阅相关频道的消费者都能够收到该消息，需要额外处理重复消费问题。

3. **为什么最后选择 Redisson 内置的延时队列来实现延时任务？**
   Redisson 的延迟队列 RDelayedQueue 是基于 Redis 的 SortedSet 来实现的。Redisson 使用 zrangebyscore 命令扫描 SortedSet 中过期的元素，然后将这些过期元素加入到就绪消息列表中。就绪消息列表是一个阻塞队列，有消息进入就会被监听到。
   
   相比于 Redis 过期事件监听方案的优势：
   - **减少了丢消息的可能**：DelayedQueue 中的消息会被持久化，即使 Redis 宕机了，根据持久化机制，也只可能丢失少量消息。也可以使用扫描数据库的方法作为补偿机制。
   - **消息不存在重复消费问题**：每个客户端都是从同一个目标队列中获取任务的，不存在重复消费的问题。

   > 跟 Redisson 内置的延时队列相比，消息队列可以通过保障消息消费的可靠性、控制消息生产者和消费者的数量等手段来实现更高的吞吐量和更强的可靠性，**实际项目中首选使用消息队列的延时消息这种方案**。

### 3.9 单元测试

**为什么需要单元测试？**

- **为重构保驾护航**：单元测试可以为重构提供信心，降低重构的成本。
- **提高代码质量**：单元测试会促进工程进行组件拆分，整理工程依赖关系，更大程度减少代码耦合。
- **快速定位 bug**：运行一次全部单元测试，找到不通过的测试，可以很快地定位对应的执行代码。
- **减少 bug**：单元测试保障工程各个"零件"按"规格"执行，从而保证整个"机器"运行正确。
- **持续集成依赖单元测试**：当持续集成服务自动构建新代码之后，会自动运行单元测试来发现代码错误。

**为什么选择 JUnit + Mockito？**

对于单测来说，目前常用的单测框架有：JUnit、Mockito、Spock、PowerMock、JMockit、TestableMock 等等。

JUnit 几乎是默认选择，但是其不支持 Mock，因此我们还需要选择一个 Mock 工具。Mockito 和 Spock 是最主流的两款 Mock 工具。

| 对比维度 | Mockito | Spock |
|----------|---------|-------|
| Mock 静态方法/私有方法 | 3.4.0 以后支持静态方法的 Mock | 不支持 |
| 代码风格 | 没有具体的结构规范，需要项目组约定 | 基于 Groovy，自带 given-when-then 规范，更清晰易读 |
| 生态与稳定性 | 使用人群广泛，SpringBoot Test 默认集成 | 相对小众 |

Mockito 和 Spock 都是非常不错的 Mock 工具，相对来说，Mockito 的适用性更强一些。

**JaCoCo 有什么用？**

JaCoCo（Java Code Coverage Library）是常用的开源代码覆盖率工具，支持生成单元测试覆盖率和接口测试覆盖率。

**JaCoCo 覆盖率报告指标：**

| 指标 | 说明 |
|------|------|
| 方法覆盖率 | 执行的方法数 / 代码总方法数，检测是否有方法被遗漏 |
| 分支覆盖率 | 控制结构的分支（如 if 语句）被执行的比例 |
| 行覆盖率 | 执行代码行数 / 总代码行数 |
| 类覆盖率 | 执行的类 / 代码中类总个数 |
| 圈复杂度 | 判断代码结构的复杂程度，一般认为大于 10 存在较大风险，严格要求不可大于 15 |

**SonarQube 有什么用？**

SonarQube 是一个基于 Java 开发的开源代码分析平台，用来持续分析和评测项目源代码的质量，可以检测出项目的代码异味、潜在错误、复杂度以及安全漏洞等问题。它还可以集成 JaCoCo 的覆盖率报告，提供更全面的代码健康评估。

> 虽然 JaCoCo 提供了详细的代码覆盖率数据，但主要关注量化测试的广度和深度。SonarQube 则提供了更全面的代码质量分析（维护性、可读性、复杂度、安全性）。将 JaCoCo 的数据集成到 SonarQube 中，可以在单一平台上评估代码的整体质量。
